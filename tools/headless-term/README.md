# ヘッドレス端末 (headless-term)

実描画デバイスも実入力デバイスも持たない端末フロントエンドです。画面内容の読み取りとキー入力の注入を
ループバック TCP 上のリクエスト/レスポンスとして公開するため、プログラム（AI や自動テスト）から
ゲームを起動・操作・観測できます。

バグの再現手順をキー列として記録し、修正後に同じ手順を再生して画面を突き合わせる、といった使い方を想定しています。

## 起動

```sh
mkdir -p /tmp/hbsave
src/hengband -mheadless --headless-port=9000 --fixed-seed=12345 \
    -ds=/tmp/hbsave -uHeadlessTest -n &
```

| オプション                    | 意味                                                                  |
| ----------------------------- | --------------------------------------------------------------------- |
| `-mheadless`                  | ヘッドレス端末を使う。`-m` を省略した場合に暗黙で選ばれることはない   |
| `--headless-port=<port>`      | 127.0.0.1 の待ち受けポート。必須                                      |
| `--headless-term-count=<num>` | 生成する端末の数 (既定 1、最大 8)。サブウィンドウを観測する場合に指定 |

再現性のために乱数シードを固定するオプションもあります。ヘッドレス端末専用ではなく、どのフロントエンドでも有効です。

| オプション            | 意味                                                       |
| --------------------- | ---------------------------------------------------------- |
| `--fixed-seed=<seed>` | 乱数の初期シードを固定する。新規キャラクター作成時のみ効く |

`-ds=<path>` でセーブディレクトリを、`-u<who>` でセーブファイル名を指定します。`-n` を付けると新規キャラクター作成から始まり、
付けなければ既存のセーブデータをロードします。

起動すると待ち受けを開始し、**最初のクライアントが接続するまでブロックします**（30 秒でタイムアウト）。
これにより、起動直後のキー入力待ちも取りこぼさずに操作できます。

### Windowsでの起動

Windows版には `-mheadless`・`-ds`・`-u`・`-n` に相当するオプションはありません。`--headless-port` を指定するだけで
ヘッドレスモードに入ります。

```bat
Hengband.exe --headless-port=9000 --fixed-seed=12345
```

**位置引数（`-` で始まらない引数）は「既存セーブファイルをダブルクリックして起動した」場合の
ファイルパス受け渡し用で、Unix版の `-n`（新規作成）とは意味が異なります。** 存在しないファイル名を渡すと
`validate_file()` が失敗して即座に `quit()` し、接続していたクライアントからは
`WinError 10054`（接続を強制的に切断された）として観測されます。新規キャラクターから始めたい場合は
位置引数を付けずに起動してください。既存のセーブファイルをロードしたい場合のみ、そのファイルの
パスを位置引数として渡します。

ゲームを終了するには `hbctl.py quit` を実行するか、プロセスを kill してください。

## クライアント (hbctl.py)

Python 3 の標準ライブラリのみで動作します。1 コマンドにつき 1 回接続します。

```sh
python3 tools/headless-term/hbctl.py info            # 端末情報とビルド情報
python3 tools/headless-term/hbctl.py screen          # 現在の画面を枠付きで表示
python3 tools/headless-term/hbctl.py screen --attrs --json  # 色属性込みの生JSON
python3 tools/headless-term/hbctl.py keys 'jjj'      # キーを送り、処理後の画面を表示
python3 tools/headless-term/hbctl.py keys '\e' --quiet      # 画面を表示しない
python3 tools/headless-term/hbctl.py state           # ゲームの内部状態 (JSON)
python3 tools/headless-term/hbctl.py messages 30     # 直近のメッセージ履歴
python3 tools/headless-term/hbctl.py replay keys.txt # キー列ファイルを一括投入
python3 tools/headless-term/hbctl.py raw '{"op":"info"}'
python3 tools/headless-term/hbctl.py quit            # ゲームを終了
```

`--host` `--port` `--timeout` `--term` は全サブコマンド共通のオプションのため、**サブコマンドより前**に
指定します（`hbctl.py screen --port 9001` のようにサブコマンドの後ろに置くとエラーになります）。

```sh
python3 tools/headless-term/hbctl.py --port 9001 screen
```

### キー列の記法

`keys` に渡す文字列は `text_to_ascii()` で解釈されるため、`.prf` ファイルと同じマクロ表記が使えます。
1 回のリクエストで送れるキー列は、変換後の長さが 1022 バイトまでです。これを超えるとエラーになるため、
長いキー列は複数回に分けて送るか `replay` を使ってください。

キー列が一部だけ注入されて意味の異なる操作になることを防ぐため、次の場合もエラーになり、
キーは 1 つも積まれません。

- 変換結果に NUL (0x00) が含まれる場合（`^@` など）。NUL はキューに積めません
- キー列そのものに NUL (0x00) が含まれる場合。そこで変換が打ち切られてしまいます
- キーキューの空きが変換結果の長さに足りない場合

表記が完結していないキー列もエラーになります。

- 末尾でエスケープの引数が足りない場合（`\` `\x` `\xA` `\01` `^` など）
- マクロトリガ表記 `\[～]` を含む場合。ヘッドレス端末は `.prf` を読まずマクロトリガを定義しないため、
  この表記はサポートしていません

| 記法   | 意味             |
| ------ | ---------------- |
| `\e`   | ESC              |
| `\r`   | CR (Enter)       |
| `\n`   | LF               |
| `\t`   | TAB              |
| `\s`   | 空白             |
| `^X`   | Ctrl-X           |
| `\xNN` | 16進のバイト     |
| `\\`   | バックスラッシュ |

### replay 用のキー列ファイル

1 行が 1 回分のキー列です。空行と `#` で始まる行は無視されます。
`--fixed-seed` と組み合わせると、同じファイルから同じ最終画面を再現できます。

```txt
# 性別a(女性) 種族a(人間)
aa
# 種族確定 職業a(戦士)
ya
```

## プロトコル

1 リクエスト = 1 行の JSON、1 レスポンス = 1 行の JSON です。文字列はすべて UTF-8 です。
`id` を指定するとレスポンスにそのまま反映されます。

レスポンスには必ず `ok` が含まれます。`ok` が false の場合は `error` にエラー内容が入ります。

`info` が返す `protocol_version` は、互換性を壊す変更を加えたときに増やします。
既存のフィールドを追加するだけの変更では増やしません。

| op         | パラメータ                           | レスポンスの主なフィールド                                   |
| ---------- | ------------------------------------ | ------------------------------------------------------------ |
| `info`     | -                                    | `protocol_version`, `system`, `version`, `japanese`, `terms` |
| `screen`   | `term` (既定 0), `attrs` (既定 true) | `width`, `height`, `cursor`, `lines`, `attrs`                |
| `keys`     | `keys` (必須)                        | `pushed` (キューに積んだキーの数)                            |
| `state`    | -                                    | `--bot-json-output` と同じ内部状態のスナップショット         |
| `messages` | `count` (既定 20)                    | `messages` (古い順の配列)                                    |
| `quit`     | -                                    | `quitting`                                                   |

### screen のレスポンス

```json
{
  "id": null, "ok": true, "term": 0, "width": 80, "height": 24,
  "cursor": { "x": 45, "y": 12, "visible": false },
  "lines": ["...80セル分をUTF-8に変換した文字列...", "..."],
  "attrs": ["0F0F0102...", "..."]
}
```

- `lines[y]` - 1 行分のセルを連結して UTF-8 に変換した文字列
- `attrs[y]` - 1 セルあたり大文字 16 進 2 桁の属性を並べた文字列。長さは常に `width * 2`

**日本語版では全角 1 文字が 2 セルを占めるため、`lines[y]` の文字数と `attrs[y]` の長さは一致しません。**
セル座標 (x) に対応するのは `attrs` 側の添字です。`lines[y]` は端末上の表示幅としては常に `width` セル分になります。

**また日本語版では、全角文字のセルの属性に色以外のビットが乗ります。** 全角文字の 1 バイト目には
0x10、2 バイト目には 0x20 が加算されるため、例えば `TERM_L_BLUE` (0x0B) のセルは `1B` `2B` になります。
色だけが必要な場合は `& 0x0f` でマスクしてください（逆に、このビットを見れば全角文字の位置が分かります）。

## 同期の保証

サーバがリクエストを処理するのは、ゲームがキー入力待ちに入った時
（`xtra_hook(TERM_XTRA_EVENT, wait=true)`）だけです。
このため `screen` で観測する画面は**必ず描画が確定した状態**になり、
「描画途中の画面を読んでしまう」ことが原理的に起きません。

`keys` のレスポンスは、キーをキューに積んだ時点で即座に返ります。
処理後の画面は続けて `screen` を投げて取得してください
（`hbctl.py keys` はこれを自動で行います）。
`-more-` 待ちのような中間の停止も、そのまま観測できます。
