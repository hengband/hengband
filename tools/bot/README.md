# ゲーム制御サーバ (bot-control)

ループバック TCP 経由で、画面内容の読み取りとキー入力の注入を公開する機能です。プログラム（AI や自動テスト）から
ゲームを操作・観測できます。

バグの再現手順をキー列として記録し、修正後に同じ手順を再生して画面を突き合わせる、といった使い方を想定しています。

**画面は普段通り表示されます。** 手元での操作もこれまで通り可能で、ソケットからの操作と併用できます。
自動操作の様子を画面で観測しながらデバッグできます。画面を出さずに動かしたい場合は
[ヘッドレス実行](#ヘッドレス実行---headless)を使います。

## 起動

```sh
mkdir -p /tmp/hbsave
src/hengband -mgcu --control-port=9000 --fixed-seed=12345 \
    -ds=/tmp/hbsave -uBotTest -n &
```

| オプション                                   | 意味                                                                      |
| -------------------------------------------- | ------------------------------------------------------------------------- |
| `--control-port=<port>`                      | 127.0.0.1 の待ち受けポート。指定しない場合は起動しない                    |
| `--fixed-seed=<seed>`                        | 乱数の初期シードを固定する (効く場面は表の下を参照)                       |
| `--headless`                                 | 画面を持たない端末を使う。`--control-port` が必須                         |
| `--headless-term-count=<num>`                | ヘッドレス実行で生成する端末の数 (既定 1、最大 8)                         |
| `--headless-term-size=<index>:<cols>x<rows>` | ヘッドレス実行で生成する端末の大きさ (既定 80x24、端末ごとに繰り返し指定) |

`--fixed-seed` は制御サーバ専用ではなく、どのフロントエンドでも有効です。
ゲームの進行に使う乱数は、新規キャラクター作成時 (`-n` で既存のセーブデータから作り直す場合を含む) にだけ
固定シードから初期化されます。既存のセーブデータでゲームを続ける場合は、セーブデータに記録された状態を引き継ぎます。
幻覚中の表示など、ゲームの進行に影響しない乱数も固定されます。こちらはセーブデータに記録されないため、
既存のセーブデータでゲームを続ける場合もゲームの開始時に初期化されます。描画で使う乱数 (幻覚中の表示や万色の
モンスターの色など) はゲームのターンや座標から決まるため、表示のモード (文字・タイル) が同じなら、端末の大きさや
サブウィンドウの構成、描き直しの回数が違っても揃います。

### JSONL出力の計測ログ

計測ログは既定では無効です。必要な場合だけ `--bot-json-timing` を追加します。

```sh
src/hengband --bot-json-output=bot-state.jsonl --bot-json-timing
```

JSONLパスに `.timing.log` を付けたファイル（例：`bot-state.jsonl.timing.log`）に、スナップショット種別・ターン・
生成／JSON変換／書込時間（マイクロ秒）・JSONバイト数を記録します。
オプションを付けなければ、既存の計測ログにも触れません。
`--bot-json-timing` 単独ではJSONL出力を有効にしません。
`--bot-json-output=-`（標準出力）や制御サーバの `state` 応答は計測ログの対象外です。
計測ログは10 MiBに達した次の書込時に切り替え、`.1`（最新）～`.3` の3世代を保持します。
古い `.3` は削除されます。行の途中では分割しないため、上限は最大1行分だけ超過します。
現在のログは起動時に空にし、バックアップは残します。ローテーション・書込に失敗した場合は
標準エラーへ通知して計測のみを停止し、JSONL出力とゲームは継続します。
JSONL本体の既存の容量制限・読込方式は変更しません。
異なるJSONLパスを使うプロセスでは計測ログも分離されます。同じJSONLパスの同時使用は避けてください。
計測ログとバックアップにはシンボリックリンク・複数のハードリンクを持つファイル・通常ファイル以外を使えません。
旧名 `emitter-timing-c2.log` は自動移行・削除しません。
JSONLのopenに2回連続で失敗すると出力を停止します。成功した時点で失敗回数をリセットします。

`-ds=<path>` でセーブディレクトリを、`-u<who>` でセーブファイル名を指定します。`-n` を付けると新規キャラクター作成から始まり、
付けなければ既存のセーブデータをロードします。**これらは Unix 版のみです**（[Windows でのセーブファイル指定](#windows-でのセーブファイル指定)を参照）。

待ち受けの開始に失敗した場合（ポートが使用中など）は、理由を標準エラー出力へ出して終了します。
接続を待たずにゲームは始まるため、起動直後の「[ 何かキーを押して下さい ]」から操作できます。

接続後、**30 秒間やり取りが無いクライアントは切断されます**。接続したまま何も送らないクライアントで
待ち受けが塞がり、`quit` すら届かなくなるのを防ぐためのものです。`hbctl.py` は 1 コマンドにつき 1 回接続して
すぐ切断するため、通常の運用で影響を受けることはありません。

### Windows での起動

`--control-port` と `--fixed-seed` は Windows 版でも使えます。診断メッセージ用にコンソールを確保します。

```bat
Hengband.exe --control-port=9000 --fixed-seed=12345
```

Windows 版は起動後、[ファイル] メニューで [新規] または [開く] を選ぶまでキー入力待ちに入りません。
**それまでソケットへの応答は返りません**。ゲームを開始してからクライアントを動かしてください。
（`--headless` を付けた場合はメニューを経由しないため、この制約はありません）

### Windows でのセーブファイル指定

**Windows 版は `-ds=<path>` `-u<who>` `-n` を実装していません。** コマンドライン解釈
（`src/main-win/commandline-win.cpp` の `CommandLine::handle()`）が解釈するのは `-o` `-r`
`--debug-console` `--output-spoilers` と `--` で始まる実行時オプションだけで、**それ以外の `-` で始まる引数は
黙って無視されます**（エラーにもなりません）。元々 [ファイル] メニューの [開く] でセーブファイルを選ぶ設計だったためです。

Windows 版で使えるのは次の 2 つだけです。

| やりたいこと | 方法 |
| --- | --- |
| 既存セーブのロード | `-` で始まらない最初の引数にセーブファイルの**フルパス**を渡す |
| 新規キャラクターの作成 | 位置引数を渡さない。保存先は**キャラクター作成時に入力した名前**で決まる |

```bat
rem 既存のセーブをロードする
Hengband.exe --headless --control-port=9000 lib\save\PLAYER

rem 新規キャラクターから始める (位置引数を渡さない)
Hengband.exe --headless --control-port=9000 --fixed-seed=12345
```

存在しないパスを位置引数に渡すと `validate_file()` が失敗して即座に終了します。接続していたクライアントからは
接続を強制的に切断されたように見えます（`WinError 10054`）。

**新規作成時の保存先は `lib/save/<キャラクター名>` に固定で、ディレクトリは変更できません。**
キャラクター名はキャラクター作成中に入力するため、クライアントから名前を送れば保存先のファイル名は選べますが、
**名前を既定のままにすると常に `lib/save/PLAYER` になります**。Windows で複数のヘッドレスインスタンスを
連続して走らせる場合、キャラクターごとに異なる名前を送らないと同じセーブファイルを共有・上書きします。

なお **Windows 版は多重起動チェック（ミューテックス）があるため、インスタンスを並行して走らせることはできません。**
2 つ目は理由を標準エラー出力へ出して非ゼロで終了します（ミューテックスはプロセスと共に消えるため、
連続して走らせる分には問題ありません）。Unix 版に同種のチェックはなく、ポートとセーブファイルさえ
分ければ並行実行できます。

## ヘッドレス実行 (--headless)

`--headless` を付けると、ウィンドウも端末も開かずに起動します。制御サーバ経由の操作だけでゲームが進むため、
CI や端末を持たない環境での自動テストに使えます。**`--control-port` が必須**で、
無い場合は理由を標準エラー出力へ出して終了します。

```sh
mkdir -p /tmp/hbsave
src/hengband --headless --control-port=9000 --fixed-seed=12345 \
    -ds=/tmp/hbsave -uHeadlessTest -n < /dev/null 2> headless.log &
```

Windows 版も同じオプションで動きます。[ファイル] メニューを経由せず直ちにゲームが始まるため、
位置引数を渡さなければ新規キャラクター作成、渡せばそのセーブファイルのロードになります。

```bat
Hengband.exe --headless --control-port=9000 --fixed-seed=12345
```

**上の例に `-ds=` `-u` `-n` が無いのは書き忘れではありません。** Windows 版はこれらを実装しておらず、
渡しても黙って無視されます。セーブファイルの扱いは
[Windows でのセーブファイル指定](#windows-でのセーブファイル指定)を参照してください。

### 通常の起動との違い

- **クライアントが接続するまで、最初のキー入力待ちで止まります。** ヘッドレス端末は取り出せる
  イベントを持たないため、接続待ちがそのまま入力待ちになります。接続は起動より後で構いません。
  裏返すと、**接続し忘れるとプロセスが残り続けます**。
- **端末の大きさは既定で 80x24 です。** `--headless-term-count` で副端末を増やせます
  （`screen` の `term` で読めます）。大きさは `--headless-term-size=<index>:<cols>x<rows>` で
  端末ごとに指定できます。主端末は 80x24 以上、副端末は 1x1 以上で、どちらも 255x255 までです。
  作る端末の数を超える添字を指定すると、理由を標準エラー出力へ出して終了します。

  ```sh
  src/hengband --headless --control-port=9000 --headless-term-count=3 \
      --headless-term-size=0:120x40 --headless-term-size=2:40x30 ...
  ```

  主端末を 80x24 より大きくすると、タイトル画面などの 80x24 で作られた画面は実際のフロントエンドと同じく
  中央に寄せて描かれます。

  起動後は `resize` op（`hbctl.py resize <width> <height>`）で大きさを変えられます。範囲は起動時と同じです。
  実際のフロントエンドでウィンドウの大きさを変えたときと同じく、地図やサブウィンドウが新しい大きさで
  描き直されます。`resize` はヘッドレス実行でだけ受け付け、それ以外ではエラーを返します
  （実際のウィンドウの大きさとゲームが扱う端末の大きさが食い違ってしまうため）。
- **アニメーションの待ちがありません。** 演出を見せる相手が居ないため、
  ゲームが要求する遅延を無視します。キー列の再生が GUI より速く進みます。
- **フロントエンド固有の `pref-*.prf` を読みません。** `info` の `system` が `headless` になるため、
  `lib/pref/pref.prf` が `$SYS` で分岐して読む `pref-x11.prf` / `pref-gcu.prf` / `pref-win.prf` が
  どれも選ばれず、フロントエンド固有のマクロトリガが定義されません（`pref.prf` 自体と、そこから
  無条件に読まれる `pref-key.prf` `pref-opt.prf` `spell-xx.prf` は通常どおり読まれます）。
  この結果、同じキー列が Unix と Windows で同じ結果になります。
- **診断メッセージは標準エラー出力へ出ます。** ゲーム側は `headless-term:`、
  制御サーバは `bot-control:` の接頭辞が付きます。
  Windows 版はコンソールを確保してそこへ出します。

- **起動直後の「[ 何かキーを押して下さい ]」を表示しません。** キーを押す相手が居ないため、
  Unix・Windows とも待たずにゲームを始めます。GUI で組み立てたキー列を再生する場合は、
  先頭のこの 1 打を取り除いてください。
- **`-s<num>`（ハイスコア表示）と `-m<sys>`（フロントエンド指定）は併用できません。**
  ヘッドレス端末と両立しないため、理由を標準エラー出力へ出して非ゼロで終了します。

## クライアント (hbctl.py)

Python 3.9 以降の標準ライブラリのみで動作します。1 コマンドにつき 1 回接続します。

```sh
python3 tools/bot/hbctl.py info            # 端末情報とビルド情報
python3 tools/bot/hbctl.py screen          # 現在の画面を枠付きで表示
python3 tools/bot/hbctl.py screen --attrs --json  # 色属性込みの生JSON
python3 tools/bot/hbctl.py keys 'jjj'      # キーを送り、処理後の画面を表示
python3 tools/bot/hbctl.py keys '\e' --quiet      # 画面を表示しない
python3 tools/bot/hbctl.py state           # ゲームの内部状態 (JSON)
python3 tools/bot/hbctl.py messages 30     # 直近のメッセージ履歴
python3 tools/bot/hbctl.py resize 120 40   # 端末の大きさを変える (ヘッドレス実行のみ)
python3 tools/bot/hbctl.py --term 1 resize 60 20  # 副端末の大きさを変える
python3 tools/bot/hbctl.py replay keys.txt # キー列ファイルを一括投入
python3 tools/bot/hbctl.py verify-subwindows  # サブウィンドウの描き直しの漏れを調べる
python3 tools/bot/hbctl.py raw '{"op":"info"}'
python3 tools/bot/hbctl.py quit            # ゲームを終了
```

`--host` `--port` `--timeout` `--term` は全サブコマンド共通のオプションのため、**サブコマンドより前**に
指定します（`hbctl.py screen --port 9001` のようにサブコマンドの後ろに置くとエラーになります）。

## プロトコル

1 行 1 JSON のリクエストに、1 行 1 JSON のレスポンスを返します。同時に接続できるクライアントは 1 つですが、
切断すれば次の接続を受け付けるため「1 コマンド 1 接続」で操作できます。

リクエストに `id` を入れると、そのままレスポンスに返されます。レスポンスは成功時 `"ok": true` と
`"result"`、失敗時 `"ok": false` と `"error"` を含みます。op ごとの中身は `result` の下に入ります。

```json
{"id": 1, "ok": true, "result": {"term": 0, "width": 80, "height": 24, "lines": ["..."]}}
{"id": 2, "ok": false, "error": "the term index is out of range"}
```

| op                  | 主なパラメータ                       | 内容                                       |
| ------------------- | ------------------------------------ | ------------------------------------------ |
| `info`              | —                                    | プロトコル版・ビルド情報・端末の一覧       |
| `screen`            | `term` (既定 0), `attrs` (既定 true) | 画面内容                                   |
| `keys`              | `keys`                               | キー列を注入する。積めたキー数を返す       |
| `state`             | `map` (既定 true)                    | ゲームの内部状態のスナップショット         |
| `messages`          | `count` (既定 20)                    | 直近のメッセージ履歴を古い順に返す         |
| `resize`            | `term` (既定 0), `width`, `height`   | 端末の大きさを変える（ヘッドレス実行のみ） |
| `verify_subwindows` | —                                    | サブウィンドウの描き直しの漏れを調べる     |
| `quit`              | —                                    | ゲームを終了する（**セーブしません**）     |

`state` の `result.type` は通常 `player_turn` です。店（我が家・博物館を含む）の画面を開いている間は、
JSONL の店のスナップショットと同じく `store` になり、`result.store` に在庫などを載せます。
JSONL と同じく、`map` の指定にかかわらず地図 (`grid_map`) を載せません（店の中ではフロアが変わらず、
店に入る前の地図と同じになるうえ、店の画面ではフロアの視界と光源の情報を消しているため）。
同じ理由で、店の中の `visible_monsters` / `detected_monsters` は視界の情報が消えた状態で作られ、店に入る前と食い違います。
JSONL の店のスナップショットは店のコマンドの入力待ちでだけ出ます（持ち物・装備の一覧を表示した後の待ちでは出ません）が、`state` は店の中のほかの入力待ち（個数の入力や
`-more-` など）でも `store` を返します。売り買いの途中では、所持品と `store` の在庫がまだそろっていないことがあるので、
在庫を読むのは `input_context` が `command` のときにしてください。

次の画面を開いている間も、`state` の `type` は JSONL のその画面のスナップショットと同じになり、同じ情報を載せます。
キャラクター情報・知識メニューの一覧・注視では、地図は `map` の指定どおりに載せます。

| 画面 | `type` | 載せる情報 | 開いている間 |
|---|---|---|---|
| キャラクター情報（`C`） | `character` | `result.character` | 名前の変更やファイルへの書き出しの入力待ちを含む |
| 知識メニューの一覧（`~` で選んだもの） | `knowledge` | `result.knowledge` | 一覧を閉じて知識メニューに戻るまで |
| 注視（`l`） | `look` | `result.look` | 注視を終えるまで |
| 呪文の一覧（`m`・`b`・`G` などの選択） | `spell_list` | `result.spell_list` | 一覧を出している間（`*` などで隠すと外れる） |
| 特殊能力・技の一覧（`U`、超能力などの `m`） | `power_list` | `result.power_list` | 一覧を出している間 |
| 思い出（注視の `r`、`/` の `r` など） | `lore` | `result.lore` | 思い出を出している間 |

キャラクター情報・知識メニューの一覧・注視は、JSONL のスナップショットは画面を開いたときに 1 回だけ出ますが、
`state` は求めた時点の状態で作ります。たとえば注視の `look` は、その時点の画面の表示範囲から求めるので、
注視の途中で表示範囲が動けば動いた後の対象になります。呪文の一覧・特殊能力の一覧・思い出は、JSONL と同じく
最後に描いたときの中身を返し、地図は `map` の指定にかかわらず載せません（JSONL と同じ）。
特殊能力の一覧（`kind` が `racial`）を出したまま `/` で使うか調べるかを切り替えても、一覧は描き直されないので、
`power_list.browse_mode` は描いたときの値のままです。今どちらで選んでいるかは、`input_context`（`spell`）の
`browse` で読んでください。
画面の中で別の画面を開いたとき（店の中でキャラクター情報を開いたときなど）は、後から開いた画面の `type` になり、
閉じると前の画面の `type` に戻ります。店の中でキャラクター情報や知識メニューの一覧を開くと地図も載りますが、
店の画面ではフロアの視界と光源の情報を消しているので、地図の視界や照明の情報は実際と合いません。
登録のない画面（所持品の一覧・品の説明など）を店の中で開いたときは、`type` は `store` のままです。

`screen` と `state` の `result.input_context` は、制御サーバが応答した時点で待っている
入力の文脈です。対応する入力待ちでは次のオブジェクトを返し、それ以外は `null` です。
キャラクター作成の初期オプションの画面や知識メニュー（`~`）の選択、設定の画面（オプション・マクロ・カラー・自動拾いエディタ）のように、
まだ文脈を公開しない入力待ちもあります。`null` は入力待ちがないことを意味しません。

| `kind` | 内容 |
| --- | --- |
| `confirm` | `prompt`: `[y/n]` などの選択肢を含む確認文 |
| `command_char` | `prompt`: 1文字入力のプロンプト |
| `string` | `prompt`, `max_length`: 入力欄に合わせて調整した内部文字コードでのバイト上限, `initial`: 初期文字列 |
| `quantity` | `prompt`, `max`: 入力後の数量の上限, `initial`: 初期数量（1） |
| `more` | `prompt`: メッセージの後に表示した `-続く-`（英語版は `-more-`） |
| `command` | `prompt`: 空文字列（持ち物・装備の一覧を表示した後の待ちでは、一覧の上の行の `持ち物： 合計 ... コマンド:` など）, `shopping`: 店（自宅・博物館を含む）の中のコマンドの入力なら `true`, `item_list`: 持ち物・装備の一覧（`i`・`e`）を表示した後の待ちなら一覧の区分（`inventory`・`equipment`）、ほかは `null` |

`{ "kind": "quantity", "prompt": "いくつですか (1-5):", "max": 5, "initial": 1 }`

`prompt` は画面に表示した文字列から前後の空白（入力欄との間を空ける空白や、行の途中に表示するための空白）を除き、UTF-8 に変換したものです。`confirm` には確認の選択肢も含みます。
`confirm` には、`[y/n]` の確認のほか、アイテムを壊すときの `[y/n/Auto]`、ペットを放すときの `[Yes/No/Unnamed]`、自殺の確認の `@` も含みます。
名前の付いたペットや乗っているペットを放すときの念押し（`本当によろしいですか？`）は選択肢を表示せず、`y`・`Y` で放し、ほかのキーでやめます。
カジノの賭けの後の `もう一度(Y/N)？` も、`y`・`Y` で続け、ほかのキーでやめます（所持金が掛け金より少なくなっていたら、`y` でもやめます）。
`/` のコマンドの `思い出を見ますか? (k:殺害順/y/n)` も `confirm` で、`y` で一覧を送る待ちに進み、`k` で殺害順に並べて進み、ほかのキーでやめます。
記念撮影（`)`）の `記念撮影しますか？ [(y)es/(h)tml/(n)o]` も `confirm` で、`y`（`Y`）でテキストをユーザーディレクトリの `dump.txt` に（確認なしで上書き）、`h`（`H`）で HTML のファイルに書き出し、ほかのキーでやめます。死亡したときの `画面を保存しますか？`（`confirm`）に `y` で答えたときも、この問い合わせが続きます。
`command_char` には、帰還先の町やダンジョン、元素の攻撃や免疫、構え、レベルアップで上げる能力値など、一覧から1文字で選ぶ待ちも含みます。
能力値の選択は ESC で取り消せず、一覧の文字のどれかを選ぶまで待ちます。
建物の中の次の待ちも `command_char` です。闘技場で賭けるモンスターの選択（`1`〜`4`）、モンスター調査の結果の送り（`r` で思い出を表示し、スペースなどで次のモンスター、`-` で前のモンスターへ送り、ESC で終える。
思い出を一度表示した後は `r` 以外のキーで終え、オプション `expand_list` が無効なら一覧の端を越えたところで終える）、
武器の比較の画面（`s` で比べる武器を変え、ほかのキーで閉じる）、ポーカーで残すカードの選択（カーソルは「決定」から始まる。`4`・`6`（`h`・`l`）でカードを選び、スペースか Enter で残すかを切り替える。
`2`（`j`）で「決定」に動かし（`8`（`k`）でカードに戻る）、スペースか Enter で決める。ESC では抜けない）。
`/` のコマンドでモンスターの一覧を送る待ちも `command_char` です（`r` で思い出の表示を切り替え、スペースなどで次のモンスター、`-` で前のモンスターへ送り、ESC で終える。
オプション `expand_list` が無効なら一覧の端を越えたところで終える）。
オプション `command_menu` が有効でコマンドメニューから選んだコマンドでは、`spell` の待ちの多く（呪文・特殊能力・剣術・ペットのコマンドなど）と、
魔道具術師・青魔道師・鍛冶師が使う種類を選ぶ `command_char` の待ちはカーソルのメニューになります（狙撃術・ものまね・弓の技などは文字で選んだままです）。
カーソルのメニューでは `2`・`8`（`j`・`k`）でカーソルを動かし（列やページが分かれているメニューでは `4`・`6`（`h`・`l`）でも動かす）、
Enter（`\r`。`\n` では決まらないメニューがある）・`x` で決め、ESC で取り消します。
練気術師が魔道書を持たずに唱える・調べるときや、盲目・暗闇で唱えるときの `'w'かESCを押してください。` と、鍛冶師のエッセンスの一覧のページ送り（スペースで次、`-` で前、ESC で閉じる）も `command_char` です。
キャラクター情報（`C`）の画面の待ちも `command_char` で、`c` で名前を変え、`f` でファイルに書き出し、`h` で表示を切り替え、ESC で閉じます。ほかのキーでは同じ待ちに戻ります。
日記（`|`）のメニューの `コマンド:` も `command_char` で、`1`〜`4` で選び、`R`（`r`）で日記を閉じて録画の開始・終了に進み、ESC で閉じます。ほかのキーではメニューを表示し直して同じ待ちに戻ります。
死亡した後の、キャラクターの記録を書き出す `ファイルネーム:` は `string` です。空のまま Enter か ESC で次に進み、ファイル名を入れると書き出してもう一度尋ねます。
これらの画面で選んだ後に続くファイル名の入力・上書きの確認・結果のメッセージなどの待ちは、それぞれの種類の文脈で返します。
`string.initial` も UTF-8 です。初期文字列は呼び出し元の指定を保持し、`max_length` に合わせた切り詰めは行いません。
数量がコマンドの引数や繰り返しから決まって入力を待たない場合、`quantity` の文脈は公開しません。
キャラクター生成前は `state` がエラーになるため、`screen` で確認してください。

`more` はメッセージ行の `-続く-` だけを表します。自己分析やアイテムの詳しい情報、死亡画面などのページ送りの `-続く-` は `any_key` で、ヘルプや知識メニューの結果などのファイルの表示と、メッセージのログのページ送りは `file` です。
`more` で送るキーは次のとおりです。スペースはそのメッセージを流します。
オプション `auto_more` が有効でメッセージのサブウィンドウがある場合は、サブウィンドウ1画面分のメッセージが流れるまで `-続く-` を省きます（`auto_more` は既定では無効です）。
ESC は次のキーを読むまでの `-続く-` を省きます（キャラクター生成前など、プレイ中でない間は省きません）。
Enter は次の `-続く-` を1回省くことがあります（長いメッセージを分割した次の断片など）。
ほかのキーは `quick_messages` が有効（既定）ならスペースと同じで、無効なら受け付けません。
流しているメッセージは `messages` で取れます。ただしキャラクター生成前のメッセージは履歴に入らないため、`screen` の1行目で確認してください。

`command` は次のコマンド（自分のターン、店の中のコマンド）の最初のキーの待ちを表します。回数の入力（`0`）とコマンドメニューは対象外で、建物（宿屋・闘技場など）の中のコマンドの待ちは `building` です。
持ち物・装備の一覧（`i`・`e`）を表示した後の待ちも `command`（`item_list` が `null` でない）で、送ったキーは次のコマンドの最初のキーになります。
ESC は一覧を閉じてコマンドの待ちに戻り、ほかのキーでは一覧を閉じてそのコマンドを実行し、アイテムを選ぶコマンドなら最初から一覧を表示します。
ただし、この待ちは `i`・`e` のコマンドの途中で、画面には一覧を重ねています。また、オプション `command_menu` が有効でも、Enter や `x` でコマンドメニューを開きません。
`\` や `^` の後と、回数の入力をスペースや Enter で終えた後の1文字の入力は `command_char`（プロンプトは `コマンド:` や `CTRL:`）で、`command` とは別の種類です。

`item` は持ち物・装備品・足元からアイテムを選ぶ待ちです。区分は `inventory`（持ち物）、`equipment`（装備品）、`floor`（足元）です。
ラベルの範囲は画面のプロンプトと同じもので、範囲の中にも選べないアイテムがあることがあります。
また、キーはラベルより先に銘のタグ（`@r1`・`@rc` など）と照らし合わせるので、タグと同じ文字を送るとタグを付けたアイテムが選ばれます。
`force` が `true` のときは、`w` はラベルではなく練気術を選びます（`w` のラベルのアイテムは、大文字の `W` を送ると確認の後に選べます）。
足元のラベルは、足元のアイテムのうちそのコマンドで選べるものだけを並べた順の位置です。`state` の `grid_map.found_items` の並びとは対応しないので、
どのラベルがどのアイテムかは `*` で一覧を表示して画面で確かめてください。足元を選んでいるときの Enter と `+` は、
足元のアイテムの並びを回すので、ラベルとアイテムの対応が変わります（文脈は変わりません）。
区分は `/`（持ち物と装備品、足元からは持ち物を優先）や `-`（足元）で切り替えます。足元に選べるアイテムが1つだけのときは、
`-` で切り替えずにそのアイテムを選ぶことがあります（足元を選んでいるときと、オプション `carry_query_flag` が無効なとき）。
`menu` が `true` のときはラベルを受け付けず、`2`・`8` でカーソルを動かして Enter で選び、`4`・`6` で区分を切り替えます。
コマンドの繰り返しなどで選ぶアイテムが決まって入力を待たない場合や、選べるアイテムが無い場合は、`item` の文脈は公開しません。
店で売る（自宅・博物館に置く）アイテムの選択は `item` ですが、店の商品（自宅・博物館のアイテム）を選ぶ待ちは対象外です。

`spell` は、呪文・剣術・ものまね・超能力などの技・特殊能力・魔道具術・青魔法・狙撃術・鍛冶師が付加する能力・ペットのコマンドを一覧から選ぶ待ちです。
ラベルの範囲は一覧のラベルの範囲で、プロンプトに範囲を表示する待ちではそれと同じです（魔道具術・鍛冶師の付加と、コマンドメニューから選んだペットのコマンド・青魔法のプロンプトには範囲がありません）。
`z` の次は `0` から続く一覧もあり、鍛冶師の付加ではページごとにラベルが `a` から始まるので、今のページの範囲を返します。
範囲の中にも選べないもの（レベルや魔力が足りないなど）や、一覧に表示しないもの（剣術・魔道具術・青魔法の覚えていないものなど）があります。
`list` が `false` のときは、スペースや `*` で一覧を表示します（もう一度送ると、隠す待ち、次のページへ進む待ち、調べる待ちで何も変わらない待ちがあります）。
`browse` が `true` のときは、選ぶと説明を表示して選び直す待ちに戻ります。
このとき、職業の技・元素魔法・狙撃術などでは前の一覧が画面に残っていても、選び直す待ちの `list` は `false` から始まります（スペースや `*` を送ると `true` になります）。特殊能力の選択では `/` で使うと調べるを切り替えます。
特殊能力と青魔法では、大文字のラベルを送ると確認の後に選びます。弓の技で作る弾の種類と、呪術の詠唱を止める呪文の選択は `command_char` のままです。

`direction` は、射撃・投擲・魔法を向ける方向や、扉を開ける・掘るなどの方向の入力です。方向はテンキーの数字（`1`〜`9`、`5` を除く）で送ります。
`can_choose_target` が `true` のとき、`*`・スペース・Enter はターゲットを対話で選び直し、`has_target` が `true` のとき、`5`・`t`・`T`・`.`・`0` は今のターゲットへ向けます。ただし、コマンドメニューから選んだコマンドでは、Enter は選び直さずに今のターゲットへ向けます。
`at_feet` が `true` のとき、`.`・`5`・`-` は足元を選びます。`has_target` が `false` のときの今のターゲットへ向けるキー（`5`・`t`・`T`・`.`・`0`。`at_feet` が `true` のときの `.`・`5` は足元を選びます）と、`has_target` と `at_feet` がどちらも `false` のときの `5` は、受け付けずに待ち直します。方向が繰り返しなどで決まって入力を待たない場合は、`direction` の文脈は公開しません。
マップの位置を確かめるコマンド（`L`）の方向の入力は `command_char` です。

`target` は、ターゲットを選ぶ画面（`*`、方向の入力の `*` など）と、見るコマンド（`l`）の待ちです。
カーソルのマスの説明を表示している間は、モンスターの思い出（`r`）や足元のアイテムの一覧を表示している間も含めて `target` です。
キーの案内は `prompt` のとおりで、主なキーは次のとおりです。
`q`・ESC で終え、`t`・`5`・`.`・`0` でカーソルのマスをターゲットにします（`free` が `false` のときは、`can_target` が `true` のときだけ）。
`free` が `false` のときは、`+`・`-` でモンスターなどの興味のあるものを順に選び、方向キーでその方向にあるものを選び、`o` で `free` が `true` のモードに切り替えます。
`free` が `true` のときは、方向キーでカーソルを 1 マス（大文字の方向キーでは半画面）動かし、`m`（スペース・`+`・`-` も同じ）で、興味のあるものがあればカーソルに近いものに戻り、`free` が `false` のモードになります。
`p` は自分のマスに戻って `free` が `true` のモードにし、`g` はカーソルのマスをトラベルの行き先にして終えます（行けないマスでは何もしません。案内に出るのは見るコマンドだけですが、ターゲットの選択でも効き、そのときはターゲットは決まりません）。
スペース・Enter・`x` は、同じマスに説明が続くとき（モンスターが持っているアイテムなど）はその説明を送ることがあります。カーソルを動かすには、`free` が `false` のときは `+`・`-` や方向キーを、`true` のときは方向キーを使ってください。
`y`・`x` は `state` の `player.y`・`player.x` と同じフロアの座標です。

`point` は、トラベル（`` ` ``）の行き先や、テレポートの行き先などの場所を指定する待ちです。
方向キーでカーソルを 1 マス（大文字の方向キーでは半画面）動かし、スペース・`t`・`.`（オリジナルのキー配置では `5`・`0` も）でカーソルのマスに決め、ESC で中断します。
カーソルが自分のいるマスにあるときは、決めるキーを受け付けずに待ち直します。
オプション `expand_list` が有効なとき（既定は有効）は、`<`・`>`（階段）、店の番号 `1`〜`9` のシフトの記号（`!`・`"` など。ローグライクのキー配置では `0`〜`9` の数字そのもの）を送ると、その地形のマスへ順にカーソルを動かします。ローグライクのキー配置では数字でカーソルを動かせないので、`h`・`j` などの方向キーを使ってください。`+` は建物のマスへ動かしますが、建物が 2 つ以上あるときは建物を選ぶメニュー（`command_char`）を開きます。

`building` は、建物（宿屋・闘技場・カジノなど）の中で、利用するサービスを選ぶ待ちです。サービスの文字と料金は画面の下の一覧で確かめ、ESC で建物を出ます。
権利の無いサービス（`(閉店)`）の文字を送ると、メッセージを表示して待ちに戻ります。所持金の足りないサービスも多くは同じですが、再充填は品物を選んでから料金を確かめます。一覧に無い文字は何もせずに待ち直します。

`file` は、ヘルプ（`?`）、知識メニューの結果、建物のルールや町の歴史などのファイルの表示で、ページを送る待ちです。
スペースで次のページ、`-` で前のページ、Enter で次の行に送ります（末尾から表示するファイルでは、この 3 つの向きが逆になります）。`2`・`8` は常に 1 行ずつ下・上に送ります。
ESC・`<` で閉じます（リンク先や `%` で重ねて開いたときは元のファイルに戻り、`q`・^Q ではまとめて閉じます）。`?` でファイルの表示のヘルプを開きます（そのヘルプを表示しているときは何もしません。`?` で開いたヘルプは `q` でもそのヘルプだけを閉じます）。
`/` で検索、`=` で強調、`#` で行、`%` でファイルへ移動し、`|` で表示している内容をファイルに保存します。それぞれの文字列の入力は `string` です。
ヘルプの目次のような、項目に英字の付いたファイルでは、その英字でリンク先のファイルを開きます（リンク先が開けなければ、メッセージを表示して `any_key` で待ちます）。

メッセージのログ（^P）のページ送りも `file` です。キーはファイルの表示と違い、`p`・スペースで古いほう、`n` で新しいほうへ 1 画面、
`8`・Enter で古いほう、`2` で新しいほうへ 1 件、`+`・`-` で古いほう・新しいほうへ 10 件送り、ESC で閉じます。
`/` で古いほうへ検索、`=` で強調し、それぞれの文字列の入力は `string` です。

`birth` は、キャラクター作成で性別・種族・職業・魔法の領域・性格を一覧から選び、能力値を決めてゲームを始めるまでの待ちです。段階は性別、種族、職業、魔法の領域（`first_realm`・`second_realm`。元素使いは `element_realm`）、性格の順に進みます。魔法の領域は、選べる領域が 2 つ以上あるときだけ選ぶ待ちになります。
プロンプトの範囲のラベルの英字を送るとその項目を選び（性格の範囲には性別で選べないものがあり、そのラベルでは選ばれずに同じ待ちに戻ります）、`*` はランダムに選びます。`2`・`4`・`6`・`8`（性別は `4`・`6` だけ）でカーソルを動かし、スペースか Enter でカーソルの項目（`*` の位置ならランダム）を選びます。
`?` でヘルプ（元素使いの領域では開かない）、`=` で初期オプションの設定を開き、`S` で性別の選択からやり直し、`Q` でゲームを終えます。
性別以外は、選ぶと説明を表示して `よろしいですか？`（`confirm`）を尋ね、`n`・`N`・ESC で同じ段階の選択に戻り、ほかのキーでは確定します。魔法の領域が 1 つしか選べないときは、選ぶ待ちと確認の代わりに `何かキーを押してください`（`any_key`）を待ちます。
前のキャラクターがあるときに最初に尋ねる `クイック・スタートを使いますか？[y/N]` は `confirm` で、`y`・`Y` で前と同じキャラクターで始め、`?` でヘルプを開き、`Q` でゲームを終え、ほかのキーで性別の選択に進みます。

性格を選ぶと、初期オプションの画面（設定の画面なので文脈はまだ公開しない。ESC で閉じる）を経て、能力値を決める段階に進みます。次の段階も `birth` で、`prompt` は画面のキーの案内です。`history`・`start` を除き、`?`・`=`・`S`・`Q` はここまでの段階と同じです。

- `stat_limits`: オプション `autoroller` が有効なときに、得たい能力値の最低値を決める画面です。`2`・`8`（`j`・`k`）で項目を選び、`4`・`6`（`h`・`l`）で値を増減し（3 と 17 の間で折り返す）、`m`・`n` で最大・最小にします。スペースか Enter で次の項目へ進み、`決定する` の上で押すか ESC で次へ進みます（`autochara` が有効なら `chara_limits`、無効なら抽選。確率が「不可能」のとき、`決定する` では進まず、ESC では進んで条件を満たさない抽選が続きます）。
- `chara_limits`: オプション `autochara` が有効なときに、年齢・身長・体重・社会的地位の最小値と最大値を決める画面です。`2`・`8`（`j`・`k`）で上下、`4`・`6`（`h`・`l`）で前・次の項目を選び（行の端では隣の行に移る）、`+`・`-`（`>`・`<`）で値を増減し、`m`・`n` でとれる範囲の最大・最小にします（最小値の欄の最大は今の最大値、最大値の欄の最小は今の最小値）。スペースか Enter で次の項目へ進み、`決定する` の上で押すか ESC で抽選を始めます。
- 抽選の間（`stat_limits`・`chara_limits` の後と、オートローラーで `roll_result` から振り直したとき）は、制御サーバが応答しません。抽選中はキーが届いているかを見るだけで制御サーバのリクエストを処理しないため、抽選が終わって `roll_result` の待ちに入ってから、届いていたリクエストに応答します。
  このため、制御サーバからは抽選を止められず、抽選の間に送った `keys` のキーは結果の画面への入力になります。確率が「不可能」のまま ESC で始めた抽選は終わらないので、ゲームを止めるしかありません。
  また、`roll_result` の待ちに入るときは（オートローラーを使わないときも）先に届いていたキーを捨てるので、条件の画面のキーと結果の画面のキーを 1 つの `keys` にまとめると、結果の画面の分は捨てられます。
- `roll_result`: 能力値の結果の画面です（オートローラーを使わなくても通る）。`r`・スペースで振り直し（オートローラーなら条件を満たすまで抽選し直す）、`p` で前の結果と入れ替え（2 回目以降。もう一度押すと元に戻る）、`h`（`H`）で表示を切り替え、Enter・ESC でこの能力値に決めます。
- `history`: 能力値を決めた後の名前の入力（`string`）に続く、生い立ちの編集です。文字を送るとカーソルの位置に上書きし（`?`・`S`・`Q` なども文字として入る）、カーソルを `^P`・`^N`・`^F`・`^B`（上・下・右・左。`keys` では矢印キーを送れない）で動かし、`^H` で前の文字を消します。`^A` で生い立ちの設定ファイルを読み込み（`confirm` の確認がある。ファイルが無いときや有効な生い立ちが無いときは、メッセージの `more` を待つ）、Enter で編集を終え、ESC で元の生い立ちに戻して終えます。
- `start`: 名前と生い立ちを決めた後の、ゲームを始めるかの確認です。`S` で性別の選択からやり直し、`Q` でゲームを終え、ほかのキーでゲームを始めます。

`any_key` は、どのキーでも先へ進む「何かキーを押す」待ちです。主に次の場面で使います。
種族・職業の能力や特殊能力の説明、読める呪文が無いときの魔法の一覧、自己分析とアイテムの詳しい情報（ページ送りを含む）、調査の魔法などでモンスターを調べた結果、
地図（自動拾いの登録が無いとき。あるときは表示する登録を `M`・`N`・`D`・`K` で選ぶ `command_char` で、ほかのキーでは地図を閉じる）、記念撮影のロード、
建物の中の賞金首の一覧と防具の評価、死亡画面とスコアの一覧のページ送り、スコアの送信の結果、セーブして終えるときと勝利して引退するときの待ち、起動直後の `[ 何かキーを押して下さい ]` の待ち、キャラクター作成で魔法の領域が 1 つしか選べないときの待ち。
死亡画面の `(ESCで中断)` のように、ESC だけ扱いが違う待ちもあります。

`keys` には `\e`（ESC）、`^X`（Ctrl+X）、`\xNN` といったマクロ表記を使えます。
マクロトリガ表記 `\[～]` は受け付けません。

プロトコル版は `4` です。版 `1` の `nearby_grids` 配列は、版 `2` で
`grid_map`（`palette` / `runs` / `cells` による圧縮地図）へ置き換わりました。
版 `3` と版 `4` の変更点は[版3での変更](#版3での変更)と[版4での変更](#版4での変更)を参照してください。
`info` と各スナップショット（JSONLを含む）の `protocol_version` は共通です。
クライアントはこれを確認し、対応していない版は拒否してください。

`state` の `grid_map`（プレイヤーが記憶している地図）はフロア全域を走査します。
地図が要らない場合は `map` に `false` を指定してください（`hbctl.py state --no-map`）。

### 圧縮地図と情報の範囲（版2〜版4）

地図は通常の地図描画で取得できる地形の観測です。トラベル処理が参照する内部地形や、過去の観測の自動補完ではありません。
描画とJSONは地形の表示判定を共有し、モンスターの暗闇・暗視・盲目・記憶表示を同じ条件で扱います。

- `w` / `h`: フロア幅・高さ。座標はゼロ起点の `y, x`。
- `palette`: `[terrain_id, flag_bits, terrain_bits, known]` の配列。
  `known` は記憶または知覚している地形を表す `1` で、現在見えているという意味ではありません。
  地形はMIMIC（見かけ）を使用し、未発見の秘密ドアなどの正体は公開しません。
  壁・扉・階段などの `REMEMBER` 地形は、画面表示と同じく `CAVE_MARK` と壁の表示条件で判定し、視界外でも保持します。
  `CAVE_KNOWN` のみでは地形を追加しません。このフラグは忘却や未観測の地形変更後にも残るため、現在の地形を知っている根拠には使いません。
  非 `REMEMBER` 地形は通常の表示判定に従い、盲目時や記憶・照明等の条件を満たさない場合は省略します。
- `runs`: `[y, x0, length, palette_index]` の配列。同じ行の連続セルのみをまとめます。
  今回取得できない地形は省略します。セル欠落は「今回の地形情報なし」であり、床の消滅・壁への変化・過去の観測の否定ではありません。
  クライアントは過去に受信した地形をフロアごとに記憶し、再観測で更新してください。フロアの切替・再生成をまたいで無条件に混ぜないでください。
  松明が離れた床の経路探索（#5516）は、この観測履歴で対応します。記憶は現在も通れる保証ではありません。
  `grid_map` 自体の欠落は地図未送信です。
- `cells`: `y, x` と追加情報を持つ疎な配列。キーは `m`=モンスターindex、
  `o`=発見済みオブジェクトのスタック数（金貨を含む）、`t`=そのtval配列、
  `s`=店番号、`e`=入口のダンジョンID、`q`=クエストID、`b`=建物種別、`p`=建物special。
  幻覚中の `t` は空配列です。
- `found_items`: `[y, x, stack_count, tval, ...]` の配列。
  地形が未知でも検知済みの品は含み、金貨・未発見品・個数0の品は除外します。
  `stack_count` は品の総個数ではなくスタック数、行長は `3 + stack_count` です。
  幻覚中は数と行長を維持し、tvalを `0`（種別不明）に置き換えます。
- `found_item_names`（版3）: `found_items` と同じ順・同じ品の `[y, x, name, ...]`。
  名前は注視コマンドが表示する名前（未鑑定品は見た目の名前）で、幻覚中は `null` です。
- `found_item_ids`（版4）: `found_items` と同じ順・同じ品の `[y, x, ids, ...]`。
  `ids` は所持品などの品と同じ `sval` / `ego_id` / `artifact_id` / `flavor_id` だけを持つオブジェクト（[版4での変更](#版4での変更)）で、幻覚中は `null` です。
- `unsafe_rows`: 地下かつ罠未調査表示（`view_unsafe_grids`）が有効な場合に高さと同数の16進文字列、それ以外は `null`。
  各行は `ceil(w / 4)` 桁で、x座標は `row[x / 4]` の下位から `x % 4` ビットに対応します。
  端数の上位ビットは0。これは罠そのものではなく `CAVE_UNSAFE`（罠未調査）です。

`flag_bits` は版3から、地図がその地形をどの照明記号で描いているかを表します
（`0`=通常記号、`1`=照明記号、`2`=暗所記号）。同じ設定済みの色と文字になる区分は最小の番号に統合するため、
これは実際の光源や暗闇の状態ではありません。例えば3区分とも同じ見た目のドアは常に `0` です。判定は地図描画と同じ条件で行い、
オプション `view_special_lite` / `view_yellow_lite` / `view_bright_lite` / `view_granite_lite` に従います
（オプションが無効なら常に `0`）。版2までは予約値 `0` でした。
内部の `CAVE_MARK` / `CAVE_KNOWN` / `CAVE_ROOM` / 照明フラグ等そのものは出力しません。
`terrain_bits` は表示対象のMIMIC地形定義から得られる静的特性です。ビット番号は以下の順序で0から割り当てます。

```text
terrain_bits:
  building, can_dig, door, down_stairs, entrance, floor, has_gold, los, move,
  permanent, quest_enter, quest_exit, stairs, store, trap, tunnel, up_stairs, wall
```

`visible_monsters` は `ml && view`、`detected_monsters` は `ml && !view` の集合です。
両方とも自身の `y, x` を持つため、地図を省略した場合や足元の地形が未知でも位置を取得できます。
地図側の `m` はセルとの関連付け用です。幻覚中はモンスターの正体・体力・状態を伏せます。
既存クライアントが地図の `m` のみから位置を復元している場合は、各モンスターの `y, x` も利用してください。

幻覚中は、モンスターの記録のほかにも画面に合わせて次を伏せます。
注視（`look`）の各マスの `items` と `carried_items` は空の配列です（注視コマンドは幻覚中にマスの中身を「何か奇妙な物」としか表示しません）。
知識メニューのペットの一覧（`knowledge.pets`）は、各行が `{index, hallucinated: true}` だけになります（画面の一覧は、ペットの名前の部分をでたらめな種族名にして表示します）。

店内スナップショットは地図を省略します。商品は店頭で公開される種類・特性を出力しますが、
自宅・博物館・所持品は通常の鑑定状態に従います。自分で付けた銘は未鑑定品でも出力します。
`player.can_see_own_grid` と `light_radius` は視認性と光源半径、`floor.feeling` は公開済みの階の雰囲気です。

`keys` に `term` はありません。キーを消費するのは常に現在の端末のため、副端末を指定する意味がないからです。

### 版4での変更

版3までは、品のエゴ・固定アーティファクト・未判明の品の見た目は、表示用の名前の文字列からしか分かりませんでした。
名前は日本語版と英語版で異なり、表示オプションでも変わるため、言語に依らない ID を追加しました。
ID はそれぞれ `lib/edit/` の `EgoDefinitions.jsonc` / `ArtifactDefinitions.jsonc` / `BaseitemDefinitions.jsonc` の `id` で、
名前はそこから引けます。出すのは品の名前に出る範囲だけで、名前から分かる以上のことは出しません。
キャラクター画面の特性のページ（能力値の維持はその 2 ページ先）に並ぶ浮遊・反射などの能力も、`player.ability_sources` に足しました（[能力の供給源](#能力の供給源)）。
あわせて、幻覚中に画面が表示しない品とペットの種族を伏せるようにしました（[幻覚中に伏せるもの](#幻覚中に伏せるもの)）。

#### 追加したキー

所持品・装備・店・自宅・博物館・`knowledge` の自宅（`items`）と装備の耐性（`equipment`）・注視（`look.grids[].items` / `carried_items`）の品（`sval` と同じオブジェクト）と、`grid_map.found_item_ids` の各品:

| キー | 出す条件 | 内容 |
| --- | --- | --- |
| `ego_id` | `known`（店の商品は常に）で、エゴのとき | `EgoDefinitions.jsonc` の `id`。`is_ego` が `true` のときだけ出る（エゴ名も鑑定するまで名前に出ない） |
| `artifact_id` | `known`（店の商品は常に）で、固定アーティファクトのとき | `ArtifactDefinitions.jsonc` の `id`。ランダムアーティファクトは固定の ID が無いので出さない |
| `flavor_id` | `aware` でなく、見た目のある種類のとき | 名前に出る見た目（`Chartreuse Potion` の `Chartreuse` など）を `flavor_name` に持つ `BaseitemDefinitions.jsonc` の行の `id` |
| `sval`（`found_item_ids` のみ） | `aware` のとき | 所持品などの `sval` と同じ。床の品の一覧には版3まで `sval` が無かった |

`flavor_id` は見た目の文字列を言語に依らず表すだけで、その品の中身を表すものではありません。見た目と中身の対応はゲームごとに
同じ tval の中で並べ替えられるので、`flavor_id` の行の名前（`name`）はその品の中身ではありません。中身は今までどおり
`aware` になって `sval` が出るまで分かりません。並べ替えない種類（`FIXED_FLAVOR`。リンゴジュースや金無垢の指輪など）は、
`flavor_id` が中身の行の `id` と一致しますが、見た目の文字列もゲームによらず同じなので、名前から分かる以上のことは分かりません。

#### 能力の供給源

`player.ability_sources` には、キャラクター画面の特性のページ（能力値の維持はその 2 ページ先）に並ぶ能力のうち、次のものを足しました。値はほかの能力と同じ
`{equipment, permanent, temporary}`（鑑定済みの装備・種族/職業/突然変異/性格・時限効果と構え）です。

| キー | 能力 |
| --- | --- |
| `hold_exp` | 経験値保持 |
| `warning` | 警告 |
| `slow_digest` | 遅消化 |
| `regenerate` | 急回復 |
| `levitation` | 浮遊。乗馬の分の `riding` も持つ（下記） |
| `reflect` | 反射 |
| `sustain_str` / `sustain_int` / `sustain_wis` / `sustain_dex` / `sustain_con` / `sustain_chr` | 腕力・知能・賢さ・器用さ・耐久力・魅力の維持 |

浮遊は乗っている馬で決まります。`levitation.riding` は、乗っていなければ `null`、浮遊する馬に乗っていれば `true`（ほかの供給源が無くても浮遊する）、
浮遊しない馬に乗っていれば `false`（ほかの供給源があっても浮遊しない）です。キャラクター画面は、乗馬中は浮遊の行の色でこれを示します。
乗馬中の浮遊は馬だけで決まるので、`levitation.temporary` は浮遊の時限効果があっても `false` になります（降りれば元に戻ります）。
突然変異の「肉体の腐敗」があると、急回復はどの供給源があっても働きません。`regenerate` はキャラクター画面と同じく特性のとおりに出すので、
種族・職業の急回復と一時の分は `false` になりますが、装備と突然変異の急回復は `true` のまま残ります。突然変異は `knowledge` の突然変異の一覧（`mutation_ids`）で分かります。
警告の装備に銘 `$` を刻むと警告は働きませんが、`warning.equipment` も同じく装備の特性のとおりに出します。銘は装備の `inscription` で分かります。

#### 幻覚中に伏せるもの

| キー | 版3まで | 版4 |
| --- | --- | --- |
| `look.grids[].items` / `carried_items` | 幻覚中も品をそのまま出す | 空の配列（注視コマンドは幻覚中にマスの中身を「何か奇妙な物」としか表示しない） |
| `knowledge.pets[]` | 幻覚中も `{index, race_id, name}` | `{index, hallucinated: true}` だけで、`race_id`・`name` のキーが無い（画面の一覧は名前の部分をでたらめな種族名にする） |

#### Python クライアントが対応すべきこと

1. `protocol_version` が `4` のスナップショットを受け付ける。
2. エゴ・アーティファクト・見た目を名前の文字列で判定している箇所は、`ego_id` / `artifact_id` / `flavor_id` と `lib/edit/` の定義で判定できる。
   キーが無いことは「名前から分からない」（未鑑定・ランダムアーティファクトなど）を表す。
3. `knowledge.pets[]` の行が `hallucinated: true` のときは `race_id`・`name` が無いので、`visible_monsters` と同じく欠落を扱う。
4. `player.ability_sources.levitation.riding` は乗馬中だけ真偽値になる（乗っていなければ `null`）。`false` のときは、ほかの供給源があっても浮遊しない。

### 版3での変更

版3は「人間が画面で認識できる情報を過不足なく出す」ための改訂です。画面に出ていない値（逆方向の漏れ）は、

使うため、フェアプレイ規則の例外として残します。人間が見られる日付・時刻は `clock` に出します。

#### Python クライアントが対応すべきこと

1. `protocol_version` が `3` のスナップショットを受け付ける（`2` は拒否）。削除したキーを `get(key, 0)` のように既定値付きで読んでいると、例外にならず `0` として誤読する（燃料0の松明・技能0等）ので、既定値を外して欠落を検出すること。
2. `inventory[]` / `equipment[]` / `store.items[]` / `knowledge` の品の `timeout` を読む箇所を `charging`（真偽）と `charging_count`（ロッドの本数）へ置き換える。
3. 同じく `fuel` を読む箇所（松明・ランタンの残量判定、燃料0の松明の除外）を `light_turns` へ置き換える。長寿命のエゴは2倍の値になり、寿命を表記しない光源（アーティファクト等）はキー自体が無い。
4. `player.skills.*` を読む箇所を `player.skill_ratings.<key>.rating`（数値が要る判定は `value`。ただし `show_actual_value` 無効時は無い）へ置き換える。`two_weapon` / `shield` の熟練は `~f` の `knowledge.skills[]` から得る（数値は `show_actual_value` 有効時のみ）。
5. `player.stats.<stat>.cur` を読む箇所を `use` / `top` / `max` / `drained` へ置き換える。
6. `character.skills.*` を `character.skill_ratings.*` へ、`character.alignment` を `alignment_label` / `alignment_value` へ置き換える。
7. 所持品等の `weapon_proficiency` が常にある前提をやめ、`weapon_proficiency_rank` を使う。
8. `knowledge` の `weapon_exp` / `skill_exp` / `spell_exp` の `exp` / `max`、`virtues[].value` が欠ける・`null` になる場合に対応する。
9. `grid_map.palette` の2番目の値を `CAVE_*` のビット列（`mark` / `cave_known` / `lite` / `view` …）として解読している箇所をやめ、表示上の照明記号番号（`0` / `1` / `2`）として読む。同じ見た目の区分は統合されるので実際の照明状態は復元できない。版2までは常に `0` だったので解読結果は全て偽だったが、版3のまま解読すると照明記号が `mark`、暗所記号が `cave_known` と誤読される。
10. JSONLの `messages` が1スナップショットで33件以上になり得る。
11. 新しい `type`（`spell_list` / `power_list` / `lore`）と `knowledge` の分類（`monsters` / `kill_count`）を、未対応なら無視できるようにする（`player_turn` と取り違えない）。
12. `player.melee` の命中・ダメージ修正と `character.ranged.to_h_b` は画面の最終値なので、武器修正や技能修正を再加算しない。攻撃できない手の `null` と、光速化中の `character.speed.base:null` を扱う。打撃回数は攻撃できない手が `0`。平均ダメージの旧 `*_x100` キーを廃止し、整数の `expected_damage_per_round` を読む（`damage_nil:true` なら `null`）。`blows` の3番目は突然変異の攻撃回数。

### quit はセーブしません

**`quit` はゲームを保存せずにプロセスを終えます。** 長時間の自動プレイの進行は失われます。
保存して終了したい場合は、ゲーム内の「セーブして終了」のキー（`^X`）を送り、
その後に出る「リターンキーか ESC キーを押して下さい。」へ ESC を送ってください。

```sh
python3 tools/bot/hbctl.py keys '^X' --quiet
python3 tools/bot/hbctl.py keys '\e' --quiet
```

ESC 以外を送るとスコアの予測表示に進んでしまい、そのままでは終了しません。
`^X` の直後の画面はセーブが終わるまで戻らないため、2 つのキーは別のリクエストで送ります。

### 応答されるタイミング

**リクエストが処理されるのは、ゲームがキー入力を待っている間だけです。** これにより、
返る画面は必ず描画が確定した状態のものになります。その代わり、長い処理やアニメーションの最中は
応答が待たされます。

### 端末の大きさ

端末の数と大きさはフロントエンドが決めます。**80x24 とは限りません。** 画面を読む前に `info` の
`width` / `height` を確認してください。`screen` の `term` にはサブウィンドウの添字も指定できます
（生成されていない添字はエラーになります）。

`lines[y]` は 1 行分のセルを連結して UTF-8 に変換した文字列、`attrs[y]` は 1 セルあたり 16 進 2 桁で
属性を並べた文字列です。日本語版では全角 1 文字が 2 セルを占めるため、`lines[y]` の文字数と
`attrs[y]` の長さ（セル数×2）は一致しません。**`attrs` 側の添字がセル座標 (x) に対応します。**
全角文字のセルの属性には色以外のビットが乗るため、色だけが必要な場合は `0x0f` との論理積を取ってください。

### サブウィンドウの描き直しの確認

サブウィンドウは、表示が変わる箇所で描き直しが要求されたものだけを描き直します。要求し忘れると古い内容が残り、
描いても画面に出す処理（`term_fresh()`）を通らないと、描いた内容が画面に出ません。
`verify_subwindows` は、コマンドの入力待ち（`input_context` の `kind` が `command`）の時点で、
サブウィンドウが 1 種類だけ割り当てられている端末ごとに次の 2 つを調べます。

- `unflushed_rows`: 描いたがまだ画面に出していない行（同じ内容で描き直しただけの行は除く）。`shown`（画面に出ている内容）と `drawn`（描いた内容）。
  `inkey()` はキーを待つ前に使っている全ての端末を画面に出す（`fresh_all_terms()`）ので、ここに出るのは、その処理がある端末を
  飛ばすようになった場合や、入力待ちの間に描いて画面に出さなかった場合です。
- `stale_rows`: サブウィンドウを全て描き直すと内容が変わる行。`before`（描き直す前）と `after`（描き直した後）

どちらの行にも、行番号 `row` と違いの種類 `difference`（文字が違えば `text`、文字は同じで色が違えば `color`、
タイルの下地だけが違えば `tile`）が付きます。行の内容は `screen` の `lines` と
同じく、端末の幅いっぱいの文字列です。`window_flag` は端末に割り当てられているサブウィンドウの種類
（`SubWindowRedrawingFlag` の値）、`was_requested` は調べる前からその種類の描き直しが要求されていた（描き直しを待っていた）か、
`consistent` はどの端末にも食い違いが無いことを表します。`was_requested` が `true` の端末の `stale_rows` は、要求の漏れではなく、
要求したのに入力待ちまでに描かれなかったことを表します。調べるときに描き直して要求が下りるので、続けてもう一度調べると
この食い違いは出ません。タイルの下地はタイルを使う端末でだけ比べます。

```json
{"consistent": false, "terms": [{"term": 1, "window_flag": 6, "was_requested": false, "unflushed_rows": [],
  "stale_rows": [{"row": 16, "difference": "text", "before": "(空白)", "after": "(新しいメッセージ)"}]}]}
```

複数の種類を割り当てた端末は、全て描き直すと最後に描いた種類の内容になって比べられないので調べません。
画面に出さない端末、ウィンドウが表示されていない端末（x11 版で閉じたウィンドウなど）、まだ使っていない端末も
調べません（`terms` が空なら何も調べていません）。ただし、調べない端末でも、調べる端末と同じ種類が割り当てられていれば
その種類が描き直されます。

`stale_rows` で分かるのは、描き直せば変わる内容の要求の漏れです。次のものは見分けられません。

- 描くたびに変わる内容: プレイヤー情報のプレイ時間（実時間）は、入力待ちから時間がたつと要求の漏れが無くても食い違います。
- 描き直しても直らない古い内容: 自分の周囲と全体図は覚えている表示から描くので、その記憶を消し忘れた古い表示は描き直しても残ります。
  思い出は、追跡しているモンスターがいないと描き直さないので、前のモンスターの思い出が残っていても食い違いません。

**調べるために、割り当てられている種類のサブウィンドウを全て描き直して画面に出すので、調べた後は食い違いが無い状態になります。**
描き直しには副作用（思い出や HP・MP の表示の比較の基準が変わる、視界内のモンスターの一覧を描くと BGM を選び直すなど）もあるため、
検証のためだけに使ってください。

店の中のコマンドの入力待ちでも調べられます。ダンジョン（町を含む）に入る前と、`input_context` が `command` でない入力待ち
（`-続く-`、ターゲットの選択、「見る」など）ではエラーになります。後者ではサブウィンドウが
カーソルの位置などに合わせた内容を描いていることがあり、描き直すと表示が変わってしまうためです。
持ち物・装備の一覧を表示した後の待ち（`item_list` が `null` でない `command`）も、コマンドの途中なのでエラーになります
（メッセージの色など、コマンドの区切りで変わる表示がまだ描き直されていません）。

`hbctl.py verify-subwindows` は食い違いを行ごとに表示し、食い違いがあれば終了コード 2、調べたサブウィンドウが無ければ 3 を
返します（`--json` で JSON のまま表示）。

### 一度に注入できるキーの数

キーキューの大きさはフロントエンドが決めます（x11 のメイン端末とヘッドレスは 1023、gcu と cap は 255、
Windows 版はより大きい）。溢れる場合は 1 つも積まずにエラーを返すため、キー列の一部だけが
実行されることはありません。長い手順は `replay` のように複数回に分けて投入してください。

## 既知の制限

- gcu 日本語版では、ノンブロッキング経路がマルチバイト入力の変換を行いません。
  そのため `--control-port` を指定している間は、端末から日本語を直接入力しても正しく扱われません
  （ソケットからのキー注入には影響しません）。ヘッドレス実行では端末からの入力自体が無いため関係ありません。
